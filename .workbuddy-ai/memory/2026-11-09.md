## Recommended a git branching strategy (docs/branching-strategy.md, OQ-13)

- Owner asked for a branching strategy recommendation. Delivered docs/branching-strategy.md
  (10.5 KB, 11 sections) as a PROPOSAL, not an approved decision; recorded as OQ-13.
- Checked real git state first: on `main` only, remote origin = github.com/almezi/singgah-web.git,
  just 2 commits (075c793 initial, 96190b3 mockup+AGENTS), NO tags, and ALL of this session's
  spec/plan/docs/design work is uncommitted (3 modified + 7 untracked paths). No commits were made.
- Recommendation: simplified GitHub Flow = one protected `main` (always deployable, owner-only
  merges) + one short-lived `build/mvp` integration branch for all implementation waves +
  `fix/<name>` after launch + a tag per deploy (`v0.1.0`, `v0.1.1`). Delete build/mvp after release.
- KEY INSIGHT that drives the design: todo.md runs 2 agents in ONE shared working directory with
  safety from "one file = one owner". A git branch is a property of the whole directory, so one
  `git switch` moves BOTH agents — branch-per-lane/agent is actively harmful. Branch by PHASE,
  not by agent. File ownership already gives the isolation. `git worktree` would allow true
  isolation but is advanced; parked.
- Mapping: Specify/Plan/Tasks (docs) → main; Implement waves 0-4 → build/mvp;
  Deploy/dogfood → merge --no-ff to main + tag + `npx vercel --prod`.
- Hard rules documented: deploy ONLY from clean tagged main (Vercel CLI ships the current working
  tree regardless of branch); never commit service_role/.env/privileged keys (anon key in
  js/config.js IS safe by design; if a key leaks rotate it, deleting the branch does not help);
  no force-push/rebase of main; spec changes land on main first then merge into build/mvp;
  consider adding .vercel/ and .zcode/ to .gitignore; do NOT delete .workbuddy-ai/.
- Rejected alternatives: GitFlow (too much machinery, no CI), branch-per-agent (breaks shared
  tree), everything on main (half-built waves + accidental deploy), plain GitHub Flow (many branch
  switches in a shared directory).
- Two things git cannot isolate: Supabase free tier = ONE project, no preview DB (schema/RLS
  changes are manual, test adds pollute the real pending queue); Vercel Git integration would
  bypass the manual gate and preview builds share the prod DB — prefer CLI deploy for MVP.

  tasks/todo.md open questions #6, docs/deployment.md §6 (rollback now uses tags),
